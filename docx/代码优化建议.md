# 代码优化建议文档

> 范围：`src/`（前端 React + TypeScript）与 `src-tauri/src/`（后端 Rust / Tauri）
> 方法论：基于"深模块（Deep Module）"设计原则 —— 小接口、大实现；复杂度藏在接缝（seam）之后，让调用方获得杠杆（leverage），让维护者获得局部性（locality）。
> 维度：代码结构 / 代码逻辑 / 代码精简

---

## 一、前端优化建议（src/）

### 1. 代码结构

#### 1.1 统一 feature 模块的文件命名规范
**问题**：各 feature 内同类文件命名风格不一致——
- `mission/MissionStore.ts`、`MissionService.ts`（PascalCase）
- `lists/listsStore.ts`、`listsService.ts`（camelCase）
- `daily-review/dailyReviewStore.ts`（目录 kebab-case + 文件 camelCase）

**建议**：统一为 camelCase 文件名（`missionStore.ts`、`missionService.ts`），与多数模块保持一致。命名一致后，跨模块检索、脚手架生成和新人上手成本都会下降。

#### 1.2 拆分超大组件文件
**问题**：多个面板组件把 UI、拖拽、弹窗、导入导出、模板逻辑全部堆在单文件：

| 文件 | 行数 |
|---|---|
| `features/lists/ListsPanel.tsx` | 1960 |
| `features/time-management/TimeManagementPanel.tsx` | 1136 |
| `features/pomodoro/PomodoroPanel.tsx` | 1080 |
| `features/habit/HabitPanel.tsx` | 863 |

**建议**：按"一个子组件 = 一个可独立理解的接口"拆分。以 `ListsPanel.tsx` 为例，可拆出 `Sidebar`（文件夹/清单树 + 拖拽）、`NoteBoard`（看板/列表视图）、`NoteImportExport`（Markdown 导入导出）、`ListContextMenu` 等子组件，每个子组件只接收所需的 props/store selector。目标是任何单文件不超过 300~400 行。

#### 1.3 明确 tiptap 编辑器"一套体系"
**问题**：项目同时存在两套编辑器体系：
- 旧体系：`components/tiptap-*`（icons 38 个、ui 28 个、primitive 25 个文件，含 `simple-editor.tsx`）
- 新体系：`features/reactjs-tiptap-v1`（基于 reactjs-tiptap-editor 封装）

两套体系并存意味着同一"编辑器"能力有两个接口、两份维护成本。

**建议**：盘点实际引用情况，确认哪套是当前主用体系；将另一套标记为废弃并删除（或移入独立分支保留历史）。若 `simple-editor` 仍被 `StandaloneNoteWindow` 等使用，先统一收口到一个 `features/editor` 门面（facade）导出，屏蔽内部实现差异，再逐步迁移。

#### 1.4 移除自制 ahooks 副本
**问题**：`features/reactjs-tiptap-v1/hooks/ahooks/` 下复制了 9 个 ahooks 的实现（`useLocalStorageState`、`useMemoizedFn`、`useEventListener` 等），与 `src/hooks/` 的通用 hooks（`use-unmount.ts` 等）功能重叠。

**建议**：要么正式引入 `ahooks` 依赖并删除本地副本；要么把真正用到的少数几个 hook 合并进 `src/hooks/` 统一维护。同一个能力只应有一个来源。

#### 1.5 CSS 组织统一化
**问题**：css / scss 混用（feature 面板用 `.css`，tiptap 组件用 `.scss`），且单文件体积偏大（`pomodoro.css` 26.7KB、`lists.css` 20.4KB），全局 `styles/` 与 feature 内样式的边界不清。

**建议**：
- 约定 feature 私有样式随 feature 目录放置，全局 token（颜色、间距、圆角）集中在 `styles/_variables.scss`。
- 大 CSS 文件按拆分后的子组件同步拆分，避免"一个面板一个千行样式表"。

### 2. 代码逻辑

#### 2.1 提取统一的 invoke 包装（最重要的一条）
**问题**：6 个 service 各自手写 `invoke` 的错误处理，模式重复且不一致：
- `listsService` / `missionService` / `dailyReviewService`：每个函数都是 `try { invoke } catch (e) { console.error; throw e }`，每个文件重复 5~10 遍；
- `habitService`：完全没有错误处理，直接 `return invoke(...)`；
- `pomodoroService`：自带 localStorage 降级逻辑，错误被静默吞掉。

**建议**：在 `src/lib/` 新增一个薄封装作为统一接缝：

```ts
// src/lib/tauriClient.ts
export async function call<T>(cmd: string, args?: Record<string, unknown>): Promise<T> {
  try {
    return await invoke<T>(cmd, args);
  } catch (e) {
    console.error(`[tauri] ${cmd} failed:`, e);
    throw e;
  }
}
```

各 service 改为一行调用：`call<MissionAllData>('mission_load_all')`。`missionService.ts` 可从 105 行缩到约 30 行；错误上报策略（日志、toast、上抛）以后只需改一处。

#### 2.2 统一 store 的乐观更新 + 同步策略
**问题**：`createSyncEngine`（keyed debounce 持久化）已经是一个设计良好的深模块，但使用不一致：
- lists / mission / daily-review / time-management / pomodoro 均使用；
- **habit 模块完全没用**，自己手写乐观更新 + 失败后 `loadAll()` 回滚，且 `createHabit`/`deleteHabit` 成功后还额外 `await loadAll()` 全量重载（多余的往返）；
- 各 store 的延迟常量（500/300）在 4 个文件里重复定义。

**建议**：
- habit store 迁移到 `createSyncEngine`，删除"成功后再 loadAll"的冗余全量刷新；
- 把 `HIGH_FREQ_DELAY = 500` / `LOW_FREQ_DELAY = 300` 移入 `createSyncEngine.ts` 导出，各 store 引用同一常量。

#### 2.3 消除 any 类型
**问题**（grep 实证）：
- `timeManagementService.ts:8`：`invoke<any>("tm_load_all")`——后端明明有确定的 `TimeManagementData` 结构；
- `pomodoroService.ts:24,27`：`(data as any).favorite_tasks`——用 any 兼容后端字段名 snake_case/camelCase 不一致，应在后端 serde `rename` 处根治（后端实际已有 `#[serde(rename = "favoriteTasks")]`，前端兼容代码可删）；
- `settings/updateStore.ts:6`：`export type Update = any`；
- `MissionStore.ts:39`：`setRoles(roles as any)`——mission 的 `Role` 和 time-management 的 `Role` 是两个形状不同的类型，用 as any 强转掩盖了类型不匹配，应定义显式的映射函数；
- `simple-editor.tsx`：多处 `(editor as any)._draggedNodePos` 访问私有属性。

**建议**：为每处 any 补上真实类型；跨模块传递的 `Role` 定义一个共享类型或显式转换函数。any 是把编译期错误推迟到运行期的债务。

#### 2.4 统一错误处理与日志出口
**问题**：`console.error` / `console.warn` 散落 30+ 处，格式各异（有的带 `[listsService]` 前缀，有的没有）；部分 catch 是空块（`catch (e) {}`），例如 `listsStore.ts` 的 BroadcastChannel 初始化、`pomodoroService` 多处。

**建议**：
- 结合 2.1 的统一 invoke 包装，日志集中在一个出口，统一前缀格式；
- 明确"静默吞错"仅允许用于真正可降级的场景（如通知权限），并加注释说明为什么可以吞。

#### 2.5 日期工具去重
**问题**：`getTodayString()`（YYYY-MM-DD 格式化）在 `habitStore.ts`、`dailyReviewStore.ts`（第 160~165 行手写拼接）等多处重复实现；`getDaysDifference` 一类的日期差值计算也是各模块自写。

**建议**：新建 `src/lib/dateUtils.ts` 收敛 `formatDateYMD(date)`、`daysBetween(a, b)` 等 3~5 个纯函数，附单元测试。

## 二、后端优化建议（src-tauri/src/）

### 1. 代码结构

#### 1.1 业务模块改为目录化组织
**问题**：每个业务文件把 DTO、SQL、tauri command 全部堆在单文件：`list.rs` 605 行（含 5 种资源的 CRUD + 迁移逻辑）、`habit.rs` 316 行、`pomodoro.rs` 287 行。

**建议**：行数尚可接受，但 `list.rs` 应拆为目录模块：

```
src/list/
  mod.rs        // 导出 commands
  dto.rs        // ListFolder / ListList / ListNote / ListTemplate + Migration*
  commands.rs   // #[tauri::command] 函数
  migrate.rs    // list_migrate_from_local（迁移属一次性逻辑，独立成文件）
```

其余模块暂保持单文件即可，避免过度拆分。

#### 1.2 拆分并压缩 local_db.rs（985 行）
**问题**：`pull_from_tidb` 与 `push_to_tidb` 各手写 15 个表的同步逻辑，每个表 30~50 行几乎相同的 `Entity::find().all()` → `ActiveModel` → `on_conflict` 样板，两函数合计约 800 行纯复制粘贴。任何新表都要在两处各加一大段。

**建议**：用泛型 + trait 把"同步一张表"抽成一个函数，这是全项目收益最大的单点重构：

```rust
async fn sync_table<E>(src: &DatabaseConnection, dst: &DatabaseConnection, upsert_cols: &[E::Column])
where E: EntityTrait, E::Model: IntoActiveModel<E::ActiveModel>
{
    if let Ok(rows) = E::find().all(src).await {
        for r in rows {
            let am = r.into_active_model();
            let mut oc = OnConflict::column(/* pk */);
            for c in upsert_cols { oc.update_column(*c); }
            let _ = E::insert(am).on_conflict(oc.to_owned()).exec(dst).await;
        }
    }
}
```

pull/push 主体收敛为 15 行"表清单"调用，预计 local_db.rs 可从 985 行压到 250 行以内。同时把"连接管理"（`establish_local_connection`）与"同步逻辑"拆到 `local_db.rs` / `sync.rs` 两个文件，职责各归其位。

#### 1.3 收敛双 schema 定义
**问题**：`schema.rs`（MySQL DDL，241 行）与 `local_schema.rs`（SQLite DDL，209 行）各自维护 12+ 张表的建表语句，字段一旦变更要同步改两处，且已有漂移迹象（如 `habits` 表 MySQL 侧靠一串 `ALTER TABLE ... ADD COLUMN` 打补丁）。

**建议**：短期在两个文件顶部互相注释引用、并写一个对比清单防止漂移；中期把每张表的列定义收敛为单一数据源（如一个描述表结构的常量表，由代码分别生成 MySQL/SQLite 方言 DDL），或引入迁移工具（sqlx migrate / sea-orm-migration）管理版本化 schema。

#### 1.4 精简 lib.rs 的 command 注册与调试命令
**问题**：
- `invoke_handler` 内联 55+ 个 command，新增/排查困难；
- `greet` 是模板残留的死代码；`pick_markdown_file` / `save_markdown_file` 等若确有导入导出功能在用则保留，否则应移除。

**建议**：删除 `greet`；核实 markdown 文件命令的前端引用后决定去留。command 列表按模块分组注释即可（Rust 宏限制下不必强行拆分注册宏）。

### 2. 代码逻辑

#### 2.1 定义统一错误类型
**问题**：所有 command 返回 `Result<T, String>`，全库 60+ 处 `.map_err(|e| e.to_string())`，错误类型信息（连接失败 / 约束冲突 / 数据损坏）在边界处即丢失。

**建议**：引入 `thiserror` 定义 `AppError`，实现 `From<sqlx::Error>` 和 `serde::Serialize`：

```rust
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("database error: {0}")]
    Db(#[from] sqlx::Error),
    #[error("{0}")]
    Other(String),
}
impl serde::Serialize for AppError { /* serialize_str(&self.to_string()) */ }
```

command 签名改为 `Result<T, AppError>`，函数体内的 `.map_err(|e| e.to_string())` 全部替换为 `?`，仅此一项就能删掉约 60 行噪音，且保留错误上下文。

#### 2.2 提取"删除 + sync_queue + 远端同步"公共函数
**问题**：以下 6+ 个 delete command 逐字重复同一套三段式样板（本地 DELETE → INSERT sync_queue → 若 TiDB 在线则远端 DELETE 并清理队列）：`tm_delete_task`、`mission_delete_role`、`mission_delete_goal`、`habit_delete`、`pomodoro_delete_record`、`pomodoro_delete_favorite`。每处 20~30 行。

**建议**：提取为一个深模块函数，成为"双库删除"这一行为的唯一实现点：

```rust
pub async fn delete_with_sync(
    sqlite: &SqlitePool, tidb: &TidbState,
    table: &str, id: &str,
) -> Result<(), AppError> { /* 三段式逻辑集中于此 */ }
```

配合表名白名单（现有 `safe_tables` 数组移到这里）防止 SQL 注入。各 command 只保留本模块特有的级联操作（如 `mission_delete_role` 先删 goals）。同时统一当前行为不一致的问题：`habit_delete` 用 `spawn` 异步同步，其他命令是阻塞同步——应统一为异步 spawn，避免离线时前端等待。

#### 2.3 统一时间格式处理
**问题**：时间表示混乱且转换逻辑分散：
- SQLite 存 ISO 字符串 `"%Y-%m-%d %H:%M:%S%.3f"`，前端要毫秒时间戳；
- `now_iso()` 在 `list.rs`、`mission.rs`、`habit.rs` 三处重复定义；
- `list.rs` 和 `time_management.rs` 各自用 `strftime('%s', ...) * 1000` 在 SQL 里转毫秒；
- `daily_review.rs` 的 `parse_ms` 要兼容 4 种输入格式。

**建议**：新建 `src/time_util.rs`：`now_iso()`、`now_ms()`、`iso_to_ms()`、`ms_to_iso()` 四个函数 + 单元测试，全库引用同一实现。长期看应统一存储格式（推荐全部存毫秒 INTEGER），消除 SQL 内转换。

#### 2.4 减少不必要的 unwrap_or_default 与 clone
**问题**：
- 行映射处大量 `row.try_get(..).unwrap_or_default()`，数据损坏时静默变成空串/0，掩盖问题。建议改用 `sqlx::FromRow` 派生自动映射（DTO 字段名与列名一致即可），既删样板又保留错误；
- `habit.rs` 为 `spawn` 准备了 5~6 个 `xxx_clone` 变量（L314-319），可将需要的字段打包成一个小 struct 一次 move；
- `lib.rs` 启动流程中的多层 pool clone 可接受（SqlitePool 内部是 Arc），无需优化，但命名可简化。

#### 2.5 启动流程的 expect 改为友好降级
**问题**：`lib.rs` L120/L123 对 SQLite 连接与建表使用 `expect`，失败即 panic 且无用户可见提示。

**建议**：本地库不可用属致命错误，panic 可接受，但至少在 expect 消息中包含 db 路径，或改为弹出错误对话框后退出，便于用户反馈问题。

### 3. 代码精简

| # | 项目 | 预计收益 |

| 1 | `sync_table` 泛型化 pull/push（见 1.2） | local_db.rs 约 -700 行 |
| 2 | `AppError` + `?` 替换 map_err（见 2.1） | 全库约 -60 行且更安全 |

## 三、跨端一致性建议

1. **字段命名契约**：后端 DTO 已普遍使用 `#[serde(rename_all = "camelCase")]`，但 `pomodoro.rs` 是逐字段 `rename`、`habit.rs` 混用两种方式。统一为结构体级 `rename_all = "camelCase"`，前端即可删除 `(data as any).favorite_tasks` 这类兼容代码。
2. **Role 类型双轨**：`mission::Role`（icon/sortOrder，时间为 ISO 字符串）与 `time_management::Role`（color，时间为毫秒）是两个不同实体却同名，前端靠 `as any` 桥接。建议后端 `tm_load_all` 返回的 role 结构与 mission 对齐（或改名 `TmRole`），前端定义显式映射。
3. **同步职责归属**：前端 `createSyncEngine`（防抖持久化）与后端 sync_queue + 60s 轮询（云同步）是两层不同的接缝，当前设计合理；建议在 README 或架构注释中明确写出这两层各自的失败语义（前端失败靠下次编辑重触发、后端失败靠队列重放），避免后续维护者误改。
